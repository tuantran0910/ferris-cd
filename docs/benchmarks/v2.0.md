## 1. What this benchmark proves

The `v1.0` benchmark (`docs/benchmarks/v1.0.md`) measured **one** controller reconciling **50**
applications / **500** resources for 30 minutes. `v2.0` raises every axis:

| Axis | `v1.0` | `v2.0` |
|---|---|---|
| Applications | 50 | **250** |
| Kubernetes resources | 500 | **2,500** |
| Control-plane shards | 1 | **3** (`--shard-id N --total-shards 3`, one `Lease` per shard) |
| Fleet generation | 250 hand-written `Application` CRs | **`ApplicationSet`s** (the `T19.3` generator) |
| Out-of-band drift | not exercised | **Drift watcher enabled** (`--enable-drift-watcher`), periodic injection + heal measurement |
| Git pressure | static repo | **periodic commits** during the soak |
| Control-plane API | not measured | **`GET /api/v1/applications` p95** measured during the soak |

The question it answers: *does the control plane stay predictable when the fleet is five times
bigger and the work is split across three shards?*

## 2. Workload profile

| Dimension | Specification |
|---|---|
| `AppProject` | `bench-scale` in the benchmark control-plane namespace, `sourceRepos: ["<repo-url>"]`, `destinations: [{cluster: in-cluster, namespace: "ferriscd-bench-*"}]`, `namespaceResourceWhitelist` limited to `ServiceAccount`, `apps/Deployment`, `Service`, `Secret`, `ConfigMap` |
| Fleet generation | `ApplicationSet`s over the fixture repository, one per bucket (`apps/bucket-<k>/*`). The CRD caps one `ApplicationSet` at **200** generated applications, so the 250-application fleet is split into buckets of 100 — a leading-digit glob over the flat layout would *not* partition correctly once the index reaches two digits. |
| Applications | 250, `spec.project: bench-scale`, `spec.source.git.path` = the generated `{{path}}`, `destination.namespace` = `ferriscd-{{path.basename}}` |
| Resources per application | 10 — 1 `ServiceAccount`, 1 `Deployment`, 1 `Service`, 1 `Secret` (exercises `stringData` normalization + redaction), 6 `ConfigMap`s → **2,500** objects total |
| Destination namespaces | 250 (`ferriscd-bench-app-01` … `ferriscd-bench-app-250`), created by `createNamespace: true` |
| Pod footprint | **zero pods.** Every `Deployment` is scaled to **0 replicas** (`--deployment-replicas 0`), which the health evaluator reports as `Healthy` ("scaled to zero replicas"). The fleet is 2,500 *resources*, not 2,500 workloads — that keeps the run inside the node's pod budget and makes the measurement about the control plane, not about the workloads. (`--deployment-replicas 1` is available for a pod-backed variant; it needs the `pause` image cached in the node, otherwise the health verdict stays `Progressing` while the image is pulled.) |
| Sync policy | `automated: {prune: true, selfHeal: true}`, `serverSideForce: false`, `pruneCRDs: false`, `pruneNamespaces: false`, `applyOutOfSyncOnly: true`, `pruneLast: true`, `requeueAfterSeconds: 30`, `revisionHistoryLimit: 10` |
| Drift stimulus | one `ConfigMap` per 50 applications is **deleted out of band** every `--drift-interval`; the harness measures the time until the object exists again with its Git value. A delete is deliberate: an in-place edit (`kubectl patch` or `kubectl edit`) records a field manager (`kubectl-patch` / `kubectl-edit`) and *takes ownership* of the field it writes, and FerrisCD applies with `serverSideForce: false` — it must not take a field away from another manager, so the controller answers `Ready=False, reason=SyncError` ("fields are owned by field manager(s) kubectl-edit which are not listed in syncOptions.takeoverFieldManagers"). That is correct behaviour, not drift it should revert. A deleted object has no field ownership: the drift watcher sees the `Delete`, triggers a reconcile, and the apply recreates it from Git. |
| Git stimulus | every `--commit-interval` the harness rewrites an **existing** key (`BENCHMARK_SUITE`) in the fixture files of every 50th application and commits. Each touched file holds 6 `ConfigMap` documents, so a commit moves 30 objects — bounded, and every one is a real revision change. (Appending a new key each time would produce a duplicate mapping key, which the guarded YAML parser correctly rejects.) |

## 3. How to run it

```bash
# 0. Safety: the harness refuses to touch anything but a kind-* context.
kubectl config current-context | grep -q '^kind-' || exit 1

# 1. Prerequisites: the CRDs and the control-plane namespace.
kubectl apply -f deploy/crds/
kubectl create namespace ferriscd-system

# 2. The acceptance run: 250 applications / 2,500 resources / 3 shards / 60 minutes.
./benchmarks/scale_250_sharded.sh \
  --apps 250 \
  --resources-per-app 10 \
  --total-shards 3 \
  --soak-minutes 60 \
  --warmup-minutes 5 \
  --sample-interval 30 \
  --commit-interval 600 \
  --drift-interval 300 \
  --control-plane-namespace ferriscd-system \
  --results-dir ./benchmark-results/v2.0

# 3. Clean the fleet up afterwards (also removes the finalizers the stopped
#    controllers can no longer run).
./benchmarks/scale_250_sharded.sh --cleanup --apps 250 --control-plane-namespace ferriscd-system
```

Offline checks (no cluster, no network):

```bash
bash -n benchmarks/scale_250_sharded.sh      # syntax
./benchmarks/scale_250_sharded.sh --self-test # partition math, YAML validity, quantile reuse
./benchmarks/scale_250_sharded.sh --dry-run --apps 10  # fixture + ApplicationSet generation
```

A short smoke run (the same code path, minutes instead of an hour):

```bash
./benchmarks/scale_250_sharded.sh --debug --apps 12 --soak-minutes 3 \
  --sample-interval 15 --commit-interval 60 --drift-interval 90 --total-shards 3
```

### What the harness starts

| Process | Command | Purpose |
|---|---|---|
| 3 controllers | `ferriscd controller --namespace <ns> --allow-local-repos --enable-drift-watcher --leader-election --shard-id N --total-shards 3 --work-root <per-shard dir> --metrics-addr 127.0.0.1:1909N` | the sharded control plane. **Only shard 0 gets `--enable-applicationsets`** — three `ApplicationSet` controllers would race on the same status subresource and log `409 Conflict`s. |
| 1 API server | `ferriscd server --api-addr 127.0.0.1:19190 --auth-policy pass-through` | measures `GET /api/v1/applications` latency. Bound to loopback with pass-through auth — a benchmark-only configuration, never a deployment. |

Every controller gets its **own `--work-root`**: the repository cache is not shared between shards,
so one shard's checkout cannot block another's.

## 4. SLOs (pass/fail)

| Metric | SLO | Where it is measured |
|---|---|---|
| Cold convergence (250 apps / 2,500 resources → `Synced` + `Healthy`) | `< 900 s` (a guardrail, not a target: the smoke runs converge in ~50 s; the threshold exists so a pathological run fails instead of reporting a number) | `kubectl get applications` poll, `wait_for_convergence` |
| Steady-state reconcile latency `p50` | `< 0.25 s` (guardrail; smoke runs measure ~0.05 s) | per-shard Prometheus histogram delta (`metrics_shard-N_post_converge.prom` → `metrics_shard-N_final.prom`) |
| Steady-state reconcile latency `p95` | **`< 1.5 s`** | same |
| Steady-state reconcile latency `p99` | reported | same |
| Per-shard RSS (post-warm-up peak) | **`< 150 MiB`** (`153600 KiB`) | `ps -o rss=` per controller PID, every `--sample-interval` |
| Per-shard open-FD delta (post-warm-up) | `<= +16` | `lsof -p <pid>` per sample |
| Drift heal latency | **`<= 60 s`** | out-of-band delete of a managed `ConfigMap` → the object is recreated with its Git value (probe resolution is the sampling interval) |
| Control-plane API `GET /api/v1/applications` p95 | reported | `curl -w '%{time_total}'` per sample |
| Metric cardinality | **`<= 9 series per application + 50`** | `crates/ferriscd-controller/src/metrics.rs` documents 6 health + 3 sync series per application; a per-resource family at 250 apps (2,500 series) exceeds the 2,300 bound |
| FD delta | `<= +16` (median of the first quarter vs the last quarter of the post-warm-up samples) | judged only with at least 20 samples — a short smoke run reports the delta without judging it |
| RSS flatness | post-warm-up peak of the second soak half `<= +10 %` of the first half's peak | same sample requirement |
| Post-warm-up samples | at least 20 per shard for the FD/flatness verdict | the 60-minute run has ~110 |
| Panics / crashes | `0` | `grep -c 'panicked at\|fatal runtime error'` over the shard logs |

The harness writes a `verdict: PASS|FAIL` line plus one `violation:` line per failed SLO into
`summary.txt` and exits non-zero — a failing soak is a failing command, not a note in a table.

## 7. What the run is allowed to prove — and what it is not

* It proves **control-plane** behaviour: convergence, reconcile latency, memory, file descriptors,
  drift handling, API latency and metric cardinality.
* It does **not** prove workload behaviour: the fleet is zero-replica `Deployment`s, `Service`s,
  `Secret`s and `ConfigMap`s on one local `kind` node. A real fleet's cost is dominated by the API server and the workloads, not by the
  controller — so the controller-side numbers here are an upper bound on the control plane's cost,
  not a capacity plan for a production cluster.
* The three shards share one API server and one node, so shard isolation is verified *logically*
  (each shard owns ~1/3 of the applications, each has its own `Lease`, each reports its own
  latency) and not by removing the shared API server from the equation.
